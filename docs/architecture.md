# Architecture

How this flake is put together. For how to add things, see
[AGENTS.md](../AGENTS.md); for how den itself works, see
[den's docs](https://den.denful.dev/).

## Loading

`flake.nix` is generated by [flake-file](https://github.com/denful/flake-file)
from the `flake-file.inputs` each module declares, and hands everything under
`modules/` to [import-tree](https://github.com/denful/import-tree). Every file
there is a flake-parts module. Files and folders starting with `_` are skipped
by the loader: they are helpers for the files beside them.

Modules share values only through `config`, so a file can move or go without
breaking another; the rules that keep it that way are in
[AGENTS.md](../AGENTS.md#designing-modules). The helpers several folders use
are read-only options their owners declare:

| Option | Owner | Holds |
| --- | --- | --- |
| `config.installTests` | `modules/flake/install-tests.nix` | `installedSystem`, `perTestedHost`, `settled`, for aspects' eval tests and checks |
| `config.isReservedKey` | `modules/den.nix` | Whether den reads a key inside an aspect as machinery rather than a child aspect |
| `config.settingsType` | `modules/den.nix` | The type of an entity's `settings`, shared by hosts and stacks |
| `config.identityType` | `modules/den.nix` | The type of an entity's `identity` (an `identities/` folder, loaded), shared by users and stacks |
| `config.hostsWith` | `modules/den.nix` | The hosts of every system that include an aspect |
| `config.perHost` | `modules/flake/eval-tests.nix` | An eval test of a probe on each of a set of hosts, failing when the set is empty |
| `config.infraStacks` | `modules/flake/terranix.nix` | Each stack's evaluated terranix config and `_meta`, for eval tests |

## Entities

Hosts are declared as `den.hosts.<system>.<name>` entities, each with its
users, `stateVersion`, settings and, for deploy targets, `deploy`. Every host
gets the same base through `den.schema.host.includes` in `modules/den.nix`:
its hostname, nix and nixpkgs settings, locale, networking and SSH. Every
user gets an account and a password from SOPS (`user-<name>-password`).

Two host options any aspect may read:

- `primaryUser`: the account that administers the host, defaulting to its
  only user. deploy-rs logs in as it, and qBittorrent's web login uses its name.
- `deploy`: present only on hosts deploy-rs targets.

`server` and `server-vm` share everything but their disk through
`modules/hosts/home-servers.nix`, which sets both entities.

A darwin host (`den.hosts.aarch64-darwin.<name>`) is an entity like any
other. Its darwin release is an integer, set in the host aspect
(`darwin.system.stateVersion`), apart from the string `stateVersion` homes
read. Its secrets are in `secrets/darwin.yaml`, decrypted with the host's SSH
key. Per-person facts (name, email, GitHub accounts) are in
`identities/<id>/git.json`; the user module names the identity.

## Aspects and roles

A feature is an aspect at `den.aspects.<category>.<feature>`, in
`modules/<category>/<feature>.nix`. A host gets a feature by including it,
directly or through a role. Roles hold `includes` only:

```
roles.home-server
├── roles.server
│   ├── roles.base: roles.core (security.sudo, cli.core), system.boot,
│   │               storage.disko, storage.impermanence, security.sops,
│   │               security.nix-access-tokens
│   ├── system.headless, system.networkmanager, system.nix-ld
│   ├── services.tailscale
│   └── security.sudo.passwordless
├── roles.media-server
│   └── services.{calibre-web, flaresolverr, jellyfin, minidlna, nginx,
│                 prowlarr, qbittorrent, radarr, recyclarr, sonarr}
├── services.restic
└── services.minecraft-server
```

Categories also sort by what the aspect configures: `cli` for a terminal tool,
`dev` for working on code, `gui` for a GUI app. A category names a concern,
never a platform; an aspect with only a `darwin` body is fine. `roles.workstation`
bundles what `workbook` runs: the machine aspects (`system.homebrew`, `dock`,
`finder`, `input`, `power`, `file-limits`, `stylix`, `security.sudo.touch-id`),
the `cli`, `dev` and `gui` aspects, and the user's `security` aspects. It also
brings the system services: `security.sops` (secrets from `secrets/darwin.yaml`),
`security.nix-access-tokens` (the GitHub token nix reads) and
`services.tailscale`. The host
adds only what is its own (`services.openvpn`, `dev.akeyless`, `dev.stacks`).

Homebrew is declared by the aspect that owns the app: its `darwin` body adds the
cask or brew, and `system.homebrew` sets the policy (no cleanup, no auto-update).
Toolchains are never global: `dev.stacks` installs a direnv library, and a
project's `.envrc` calls `use_stack jvm` or `use_stack node`. A test pins that no
JDK, node or their variables reach `environment.systemPackages` or the home.

An aspect in `den.schema.<kind>.includes` reaches the host, but its `homeManager`
body does not reach users: only aspects in the host's include tree are routed to
them (`den.batteries.host-aspects`). Such an aspect is also included from a role,
as `security.ssh` is in `roles.workstation`.

Aspects that build on the same thing include a shared aspect, which den
includes once: every media aspect includes `services.media`, which owns the
media root and the `media` group, and every aspect that reads a secret
includes `security.sops`. An aspect that only adapts to another one is a
conditional variant: `security.sops` includes `security.sops.impermanent`
(the host key read from the persistence root) through `den.lib.policy.when`,
only where `storage.impermanence` is present. Near-identical aspects come from one
factory: `services/_arr.nix` builds sonarr, radarr and prowlarr, each a
whole aspect.

## Settings and quirks

Per-host tunables are settings of the aspect that reads them:
`system.locale.{timeZone,locales,layouts}`,
`system.networking.{domains.{lan,tailnet,public},knownNetworkServices}`, `dev.stacks.node.npmRegistry`,
`services.openvpn.connections`,
`services.media.root`, `services.restic.bucketUrl`,
`storage.disko.{device,encrypted,swapSize}`, `storage.impermanence.root` and
minecraft's players and rules. Hosts set only the ones that differ from the
default.

Data that many aspects contribute and one collects travels as quirks:

| Quirk | Contributed by | Collected by | Becomes |
| --- | --- | --- | --- |
| `persist` | every aspect with state | `storage.impermanence` | `environment.persistence`, and the guard's list of accepted paths |
| `vhosts` | each proxied service | `services.nginx` | one virtual host per entry at `<name>.<domain>` |
| `backup` | jellyfin (excludes its cache), calibre-web (adds the book library) | `services.restic` | extra backup paths and excludes |
| `installChecks` | most aspects; nginx derives its own from the rendered vhosts | `storage.disko` | the install test's checks |

A quirk value may be a function of the host (`{ host, ... }:`, as calibre-web's
`backup`) or of the evaluated config (`{ config, ... }:`, as nginx's
`installChecks`).

## Packages

nixpkgs follows `nixos-26.05`. `pkgs.unstable` is `nixos-unstable` with the
same config, used where a service needs newer releases: the *arr apps,
FlareSolverr, Recyclarr and the Minecraft server. Both inputs are pinned in
`flake.lock`; `server`'s eval tests pin them to the revisions the live box
was built from, so updating them is a deliberate change.

## Storage

`storage.disko` lays out one disk: a 1 GB EFI partition at `/boot`, then
btrfs (inside LUKS unless `settings.storage.disko.encrypted = false`) with
these subvolumes:

| Subvolume | Mount | Lifetime |
| --- | --- | --- |
| `@root` | `/` | Reset to the empty `@root-blank` snapshot at every boot |
| `@nix` | `/nix` | Kept |
| `@log` | `/var/log` | Kept |
| `@swap` | `/swap` | Swapfile |
| `@persist` | `/persist` | Kept: the state services declare with `persist` |
| `@home` | `/home` | Kept |
| `@data` | `/data` | Kept: downloads and the media library |

The reset runs in the initrd (`impermanence-rollback-root`), before `/` is
mounted. Anything outside the kept subvolumes is gone after a reboot unless an
aspect persists it, which impermanence bind-mounts from `/persist`. The host's
SSH key, and with it its SOPS identity, is one of those files.

## Tests

- **Eval tests**: `evalTests.<name> = { expr; expected; }`, declared beside
  the code they pin and collected into `checks.<system>.eval-tests`.
- **Parity**: `modules/hosts/server/` holds fixtures generated from the
  evaluated config of the snowfall tree `server` ran before (`_services-master.json`,
  `_disko-master.json`, `_filesystems-master.json`). The tests compare users,
  groups, firewall, virtual hosts, backups, secrets, networking, locale,
  service units and the disk layout with them, and the persisted paths with
  the live box's state.
- **Darwin**: `checks.aarch64-darwin` holds the eval tests. `just build <host>` builds the system.
- **Stacks**: `checks.<system>.stacks-<host>`, for every host including
  `dev.stacks`, sources the library that host installs and checks its
  registry setting.
- **Infra stacks**: each stack's rendered config is compared with the one
  snowfall last applied (`modules/infra/_parity-<stack>.json`), and its
  declared secrets are pinned; `checks.<system>.infra-<stack>` runs the
  import-target check. `just infra-validate` needs the secrets, so it is not
  part of `just check`.
- **Packages**: each `packages/<name>` runs its tests in `checkPhase`;
  `checks.<system>.package-<name>` builds it.
- **Install tests**: `modules/flake/install-tests.nix` installs every host
  that includes `hardware.qemu-guest` into disko's test VM, with throwaway
  secrets. The test checks the boot, accounts and passwords, then
  power-cycles the VM and checks that root was wiped and persisted state
  survived. It then runs the aspects' `installChecks`, waits for the system
  to settle, fails on any failed unit, and finally runs the undeclared-state
  guard, which fails on any entry under `/var/lib` or `/var/cache` that is
  neither persisted nor listed in `persist.ignore`.
- **Naming**: `modules/flake/naming.nix` checks that aspect paths mirror
  file paths, that no path segment is a key den reserves, and that imports
  stay in their folder.

## Infra stacks

Cloud and API resources are OpenTofu stacks, a den entity kind of their own
declared in `modules/flake/terranix.nix`: `den.stacks.<name>` (kind
`den.schema.stack`, inheriting `den.schema.conf`), resolved from the flake
root like hosts. A stack takes `settings` like a host, and aspects take it as
`stack`. A stack managing a person's accounts declares whose with `identity`,
as a user does (`github` derives the repository owner from it).

Every stack includes `den.aspects.infra.<name>` (`modules/infra/<name>.nix`)
and `infra.state`. Their `terranix` bodies, and those of the provider aspects
they include (`infra.cloudflare`, `infra.tailscale`), are collected per stack into
`flake.terranixModules.<name>` and rendered by terranix's flake module:
`packages.<system>.<name>` runs `tofu apply`, with `.plan`, `.destroy`,
`.init`, `.config` (the rendered `config.tf.json`) and `.terraform` (the
wrapper) beside it.

The wrapper runs from the repo root and works in `infra/<name>`, where the
encrypted `terraform.tfstate`, `.terraform.lock.hcl` and the stack's
`secrets.yaml` (`state-passphrase`) are committed. Before each `tofu` call it
decrypts every secret the stack's bodies declare in `_meta.secrets`
(`TF_VAR_<var> = { file; key; }`; provider credentials live once in
`infra/secrets.yaml`) and writes `encryption.tf`, the HCL state-encryption
block (pbkdf2 + aes_gcm) that JSON can't express. `infra.state` declares the
passphrase variable and secret. `checks.<system>.infra-<name>` fails on an
`import` whose target is not a resource of the stack.

A stack learns about hosts through quirks, never by reading evaluated host
configs: `tailnet` collects `tailnet-tags`, which `services.tailscale`
contributes from each host's `tags` setting, with a `pipe.collectAll` policy
on the stack entity: collect policies go in `den.stacks.<stack>.includes`;
included from the stack aspect they do not fire.
`dns` collects `published-names`, the FQDNs nginx and Minecraft contribute,
from hosts with `deploy` only, with provenance for each name's hostname.

## Deploys

`modules/flake/deploy.nix` turns every host with `deploy` into a deploy-rs
node. It logs in as the host's `primaryUser`, and `interactiveSudo` follows
whether sudo needs a password. `just deploy <host>` builds on the target;
`just deploy <host> --boot` installs the generation for the next boot
without switching to it.

## Installer image

`iso-x86_64` is a host like any other, built as a bootable image instead of
installed. It includes `roles.core`, the part of `roles.base` that needs no
disk layout or secrets (sudo and `cli.core`'s rescue tools), and
`system.iso`, which imports nixpkgs' minimal installer profile. On the image
the primary user autologins with passwordless sudo, NetworkManager drives
Wi-Fi, and root accepts the users' identity keys over SSH so nixos-anywhere
can install from it. It is the only host where root may log in; every other
host keeps `PermitRootLogin = "no"` (`sshd-no-root-off-images`). It carries
no secrets: with no host key it could decrypt nothing, so `system.iso`
excludes `security.user-password`, and the account has no password. Its eval
tests run over every host that includes it, and `nix run .#<host>` wrappers
skip image hosts, since switching a running machine to one would replace its
system.

CI's `iso.yml` builds the image and uploads it as an artifact named after
the host; `just iso-build` builds it on Linux, `just iso-fetch` downloads
master's latest, and `just iso-write` writes either through
`packages/iso-write`. That writes only to a whole USB or removable disk: it
refuses partitions, internal disks (built-in SD slots too) and macOS virtual
disks, and requires the device to be typed back. An aarch64 image is one more host,
`iso-aarch64` under `den.hosts.aarch64-linux`, plus `aarch64-linux` in
`systems` and a matrix row on an arm runner.
