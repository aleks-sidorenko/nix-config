# AGENTS.md

Guidance for coding agents working in this repository.

## Overview

NixOS hosts declared with [den](https://den.denful.dev/), a dendritic
flake-parts layout. Every `.nix` file under `modules/` is a flake-parts module
loaded by import-tree; `_`-prefixed files and directories are helpers the
loader skips. `flake.nix` is generated by flake-file.

Four den concepts; read den's docs, not this file, for how they work:

- **Entities**: hosts (`den.hosts.<system>.<name>`) and users
  (`den.hosts.<system>.<name>.users.<user>`, content in `den.aspects.<user>`).
- **Aspects**: units of configuration, `den.aspects.<path>`, with a class body
  per target (`nixos`, `homeManager`) and `includes`.
  See [overview](https://den.denful.dev/overview/) and
  [settings](https://den.denful.dev/guides/aspect-settings/).
- **Policies**: how aspects reach entities (`den.schema.<kind>.includes`,
  `den.default`, `provides.to-hosts`).
- **Quirks**: typed collections aspects contribute to and class bodies read
  (`den.quirks`; see [quirks](https://den.denful.dev/guides/quirks/)).

Hosts: `server` (real, x86_64), `server-vm` and `base-vm` (QEMU guests,
install-tested in CI).

## Where things go

| Need | Mechanism | Place |
| --- | --- | --- |
| Reusable config for one concern | feature aspect | `den.aspects.<category>.<feature>` in `modules/<category>/<feature>.nix` |
| A bundle of features | role aspect | `den.aspects.roles.<role>` in `modules/roles/<role>.nix`, `includes` only |
| Applies to every host / user | schema include | `den.schema.host.includes` / `den.schema.user.includes` in `modules/den.nix` |
| Per-host value an aspect needs | setting | `settings` on the aspect; set in `den.hosts.<system>.<host>.settings.<category>.<feature>` |
| Per-host fact for any aspect (stateVersion, deploy) | host option | `den.schema.host.options` |
| State kept across reboots | `persist` quirk | `persist.directories` / `persist.files` in the aspect |
| Extra install-test assertion | `installChecks` quirk | Python snippets in the aspect |
| Test-VM-only config an aspect needs | `disko.tests.extraConfig` | inside the aspect's `nixos` body |
| User-owned system config (password secret) | `provides.to-hosts` | user-side aspect, `modules/security/user-password.nix` |
| Host identity and its tests | host module | `modules/hosts/<host>/default.nix` (`_` helpers beside it) |
| Flake outputs, checks, tooling | flake-parts module | `modules/flake/<name>.nix` |
| Pure helpers | plain function | `modules/_lib/<name>.nix` |
| Shared constants | plain attrset | `modules/storage/_layout.nix` (disk label and subvolume names, defined once) |
| Secrets | SOPS | `secrets/nixos.yaml`; recipients in `.sops.yaml` |

Hostnames, usernames, `/persist` and domains appear only in `modules/hosts/`,
`modules/users/`, entity declarations and option defaults, never in a feature
aspect. The persistence root is the `storage.impermanence.root` setting; read
it, never write the path.

## Naming

- `den.aspects` top level holds only hosts, users and categories.
  Categories: `system`, `storage`, `security`, `services`, `hardware`, `roles`.
- Feature: `den.aspects.<category>.<feature>` mirrors
  `modules/<category>/<feature>.nix` (or `<feature>/default.nix` when it has
  variants or helpers). Variant: `<category>.<feature>.<variant>` mirrors
  `modules/<category>/<feature>/<variant>.nix`.
- A category holds nothing itself and is never included. No namespace.
- Hosts and users are never named after a category.
- No path segment may be a den reserved key: `name description meta includes
  excludes admits policyEnforcement provides policies into classes _module _`,
  anything starting `__`, `settings`, any class (`nixos darwin homeManager os
  user hjem maid wsl`), any quirk (`persist installChecks`). Declaring a new
  quirk or class reserves its name too.
- Include named aspects (`den.aspects.system.nix`), never inline modules in
  `includes`.

`modules/flake/naming.nix` enforces this with eval tests; `just check` fails
on a violation.

## How to add

Stage new files (`git add`) before `just check`.

### A feature

1. Create `modules/<category>/<feature>.nix` with
   `den.aspects.<category>.<feature> = { nixos = …; };`. The file path mirrors
   the attribute path.
2. Declare each flake input it needs in the same file
   (`flake-file.inputs.<name>.url = "…";`), then `just flake-write`.
3. Include it from a role (`modules/roles/*.nix`), a host aspect, or
   `den.schema.<kind>.includes` in `modules/den.nix` if it applies to all.
4. State that survives reboot: `persist.directories = [ … ];`.
   An install-test assertion: `installChecks = [ ''machine.succeed("…")'' ];`.
   A test-VM accommodation (no network, no real secrets):
   `disko.tests.extraConfig.<option> = lib.mkForce …;` in the `nixos` body
   (see `modules/services/tailscale.nix`).
5. Add `evalTests.<feature>-<what> = { expr = …; expected = …; };` in the
   nearest test-owning module (`modules/hosts/*/default.nix`,
   `modules/users/*.nix`, or `modules/flake/*.nix`).

### A host

1. Create `modules/hosts/<host>/default.nix` with
   `den.hosts.<system>.<host> = { users.<user> = { }; stateVersion = "…"; settings.storage.disko.device = "…"; };`
   and `den.aspects.<host>.includes = [ den.aspects.roles.<role> … ];`.
2. Hardware-specific config goes in `modules/hosts/<host>/_hardware.nix`,
   imported via the host aspect's `nixos.imports`.
3. deploy-rs node: `deploy.sshUser = "<user>";` on the host (optional
   `deploy.hostname`). `deploy = null` (default) means no node;
   `modules/flake/deploy.nix` derives `interactiveSudo` from
   `security.sudo.wheelNeedsPassword`.
4. Add the host key to `.sops.yaml`, then `sops updatekeys secrets/nixos.yaml`.
5. Add eval tests beside it. A host replacing a live one needs a parity test
   like `modules/hosts/server/_parity.nix`.

### A VM host

1. As a host, named `<name>-vm` for the host it stands in for, including
   `den.aspects.hardware.qemu-guest`, with
   `settings.storage.disko.device = "/dev/vda"`.
2. `modules/flake/install-tests.nix` adds `checks.install-<host>` for every
   host including `qemu-guest`; no extra wiring.
3. Add an eval test that `config.allSystems.x86_64-linux.checks ? install-<host>`.
4. The install test itself runs in CI only (`just vm-test <host>` needs
   x86_64 KVM).

### A user

1. `den.hosts.<system>.<host>.users.<user> = { };` in the host module.
2. `modules/users/<user>.nix`: `den.aspects.<user>.includes = [ … ];`
   (`den.batteries.primary-user`, `den.batteries.user-shell "fish"`, …).
3. Public keys in `identities/<user>/`; the password hash as
   `user-<user>-password` in `secrets/nixos.yaml` (`sops secrets/nixos.yaml`).
4. Eval test beside the user (groups, shell, key).

### A setting

1. In the aspect: `settings.<name> = lib.mkOption { type; default; description; };`
   (see `settings.root` in `modules/storage/impermanence.nix`).
2. Read in a class body: `host.settings.<category>.<feature>.<name>`.
3. Override per host: `settings.<category>.<feature>.<name> = …;` on the
   `den.hosts.<system>.<host>` entry.

### A quirk

1. `den.quirks.<name>.description = "…";` in `modules/den.nix`.
2. Contribute from aspects as `<name> = [ … ];`; read it by taking `<name>` as
   a class-body argument (see `persist` in `modules/storage/impermanence.nix`).
3. Its name is now reserved; `just check` reports any existing path segment
   that clashes.

### An input

1. Declare `flake-file.inputs.<name>.url = "…";` in the module that uses it,
   with `inputs.nixpkgs.follows = "nixpkgs";` where the input has one.
2. `just flake-write`; stage `flake.nix` and `flake.lock`.
3. Never hand-edit `flake.nix`; `just check` fails when it is stale.

## Rules

- No `enable`-gated aspects, no `mkIf` on roles: a host gets a feature by
  including it.
- No `specialArgs`, no `with`, no legacy den API (`provides`/`_` other than
  cross-entity keys like `provides.to-hosts`, `den.ctx`, `den.lib.parametric`,
  `den.base`).
- No hostname, username, `/persist` path or domain in a feature aspect.
- No `._` in aspect names; helpers are `_`-prefixed on disk only.
- `/home` is its own persistent subvolume; the only persistence quirk is
  `persist`. `installChecks` holds install-test Python only.
- An aspect owns its install-test accommodations (`disko.tests.extraConfig`);
  hosts and the harness do not special-case aspects.
- `server`'s disk must keep matching master's layout (parity tests); change it
  deliberately, together with the parity fixtures.
- Never commit secrets; respect SOPS. Move secrets files, do not re-encrypt.
- Install tests run in CI only. On darwin `just check` evaluates them without
  building.

## Commands

Recipes use the dev shell directly when inside `nix develop` and fall back to
it otherwise.

```bash
just check            # format-check + lint + flake-check (stale flake.nix, eval tests)
just format [path]    # nix fmt (writes)
just format-check
just lint             # statix + deadnix
just lint-fix
just flake-write      # regenerate flake.nix from flake-file.inputs
just flake-check      # nix flake check
just build <host>     # build a host's toplevel
just vm-test <host>   # install test; x86_64 Linux with KVM only (exits 1 elsewhere)
just update [input]   # nix flake update
nix run .#<host> -- switch   # nh wrapper per host
```

Recipes are `<group>-<suffix>`; within a group every suffix is the same kind
(verbs for resource groups: `format-check`, `lint-fix`). Rename old recipes
instead of aliasing.

Updating den: `just update den`, read den's
[whats-changed](https://den.denful.dev/whats-changed/), fix what it names,
`just flake-write`, `just check`; one PR.

Debugging: `nix eval .#nixosConfigurations.<host>.config.<path>`; see den's
[debug guide](https://den.denful.dev/guides/debug/).

## Code style

- `inherit` over `with`; no `with` anywhere.
- Comments say why, not what; terse, no vendor or host names.
- Stage new files before evaluating: flakes ignore untracked ones.
- `just format` before each commit.
- Match surrounding style.

## Git

- Conventional Commits: `<type>[(scope)][!]: <description>`; types `feat fix
  docs refactor chore test style ci perf build`.
- Branches `<type>/<short-kebab-description>`, named after the goal; PRs are
  based on `master` with a Conventional Commits title.
